# Trusted WebKit Dispatcher Contract

**Status:** implementation contract for a follow-on to Director native-runtime PR #164  
**Base:** `codex/bridge-native-runtime-integration` at `6661bf655edef85e94fa1f363fcf54a33f20233c`  
**Purpose:** define the security boundary required before any web page can request native model operations.

This document is a design/acceptance contract. It does not claim that WebKit dispatch is implemented or enabled.

## Current verified boundary

- `WorkspaceView.swift` creates a `WKWebView` and enforces same-origin navigation, but installs no script message handler.
- `BridgeGate.parse` validates message shape, action allowlists, and origin when supplied by its caller. The caller must obtain the page/frame origin from WebKit, never from message JSON.
- `BridgeChallengeStore.issue` and `consume` provide a host-owned, one-use challenge bound to origin, request UUID, runtime session UUID, and expiry.
- `RuntimeController.generate` validates that `challengeNonce` is a well-formed token and includes it in an unsigned candidate. It does not consume or validate a challenge-store entry.
- Consequently, direct access to `RuntimeController.generate` is not proof of bridge authorization. The dispatcher is responsible for consuming the challenge before it calls generation.

## Required component boundary

Introduce a host-owned dispatcher/coordinator between WebKit and `RuntimeController`. It must own or receive explicit references to:

1. The immutable trusted workspace origin selected by the native host.
2. The `BridgeChallengeStore`.
3. The active runtime-session identity, read from native runtime state.
4. The bridge parser/strict action schema.
5. A native approval coordinator for consequential actions.
6. The `RuntimeController` instance.

Do not place this authority in JavaScript, page-provided JSON, model output, or a browser-visible boolean.

## WebKit ingress requirements

- Install the handler only in the intended page content world and under a fixed, documented message-handler name.
- Accept messages only from the main frame.
- Derive the source URL and security origin from `WKScriptMessage.frameInfo`; never trust a URL/origin field in the message body.
- Require exact scheme/host/effective-port match with the host's trusted origin. Reject redirects or navigations that leave that origin.
- Reject subframe messages, opaque origins, malformed bodies, unknown actions, unknown fields, missing fields, oversized values, and invalid identifiers.
- Do not expose the handler to arbitrary frames or untrusted content worlds.
- Remove the handler during teardown and invalidate outstanding challenges when the trusted page changes, the web view is replaced, the runtime session changes, or the workspace is closed.
- Keep the existing iOS 16 deployment target in mind. If using `WKScriptMessageHandlerWithReply`, verify availability against the actual SDK and retain a fail-closed callback implementation only if needed.

## Challenge protocol: generation

1. Native host determines the active trusted page URL, native request UUID, and active runtime session UUID.
2. Native host issues a challenge through `BridgeChallengeStore.issue(page:trusted:requestId:sessionId:)`.
3. The challenge is returned only to the trusted main-frame page for that specific request; it is not generated by JavaScript.
4. The incoming generation message is parsed using the frame-derived page URL and strict schema.
5. Native dispatcher verifies that message request UUID and session UUID equal the host-owned pending request/session binding.
6. Native dispatcher calls `BridgeChallengeStore.consume` with the frame-derived page URL, trusted URL, request UUID, and native session UUID.
7. Only after successful consumption may the dispatcher invoke `RuntimeController.generate`, passing the consumed nonce and the exact bound identifiers.
8. A second message, replay, expiry, mismatched origin, mismatched request, or mismatched session must fail before generation.
9. The response is an unsigned generation candidate only. It must not be represented as a signed receipt, attestation, authorization grant, or proof.

Challenge consumption must happen before generation begins. Do not make challenge validation an optional callback that callers can omit. Prefer a single dispatcher API that is the only bridge-facing generation entry point; keep lower-level runtime APIs unavailable to untrusted call paths.

## Approval protocol for consequential actions

- `importModel`, `loadModel`, and `unloadModel` are consequential and remain disabled until native host approval is integrated.
- Approval must be an explicit native-host decision bound to the exact action, exact validated parameters, active page origin, runtime session, and short expiry.
- Do not accept `authorized: true`, `consequentialAuthorized: true`, or any other page-supplied boolean as approval.
- A model/agent-generated proposal is untrusted input and cannot approve itself.
- Approval must be consumed once and must not be transferable to a different action, model, file hash, or session.
- If the approval UI/coordinator is absent, unavailable, cancelled, stale, or cannot bind all parameters, reject the action.
- Do not add import or file-picker authority as a side effect of implementing generation dispatch.

## Action policy for initial release

| Action | Initial dispatcher policy |
|---|---|
| `getRuntimeStatus` | Read-only; main-frame trusted-origin only |
| `listModels` | Read-only; main-frame trusted-origin only |
| `validateModel` | Read-only validation; no import/load side effect |
| `checkReadiness` | Native session-bound probe; rate-limited and cancellation-aware |
| `generate` | Challenge-bound one-use dispatch; requires valid active readiness |
| `cancelGeneration` | Only cancel a request owned by the active native session |
| `importModel` | Disabled until explicit host approval and separately reviewed file-import contract |
| `loadModel` | Disabled until explicit host approval bound to model identity/hash |
| `unloadModel` | Disabled until explicit host approval; must release only the exact native lease |

Unknown actions fail closed. No action may create a signer, receipt, APEX grant, device attestation, or evidence authority.

## Required tests before enabling dispatch

### Origin and frame
- Trusted main-frame message accepted.
- Foreign scheme, host, or effective port rejected.
- HTTP non-loopback rejected; HTTP loopback follows the explicit development policy only.
- Same-origin redirect remains valid; cross-origin redirect is rejected.
- Every subframe message rejected.
- Message body cannot override the frame-derived URL/origin.

### Schema and bounds
- Unknown action and unknown field rejected.
- Missing required field, wrong JSON type, malformed UUID/token, oversized prompt, invalid token count, NaN/infinite/out-of-range temperature rejected.
- Nested/ambiguous values are rejected unless explicitly part of a documented schema.

### Challenge lifecycle
- Missing, fabricated, expired, replayed, wrong-origin, wrong-request, and wrong-session challenges rejected.
- A failed binding attempt does not consume another request's valid challenge.
- Successful consumption occurs exactly once and before exactly one call to generation.
- A generation error after consumption does not restore the challenge.
- Page navigation, web-view teardown, runtime-session replacement, and workspace closure invalidate pending challenges.
- Direct generation dispatch without going through the host dispatcher is not reachable from WebKit.

### Approval
- Page-supplied booleans never authorize consequential actions.
- Approval for one action/model/hash/session cannot authorize another.
- Cancelled, expired, missing, or stale host approval rejects.
- Import/load/unload remain disabled when approval integration is absent.

### Lifecycle and response
- Handler is removed on teardown.
- In-flight task cancellation reaches the native runtime drain path.
- Responses are correlated to the originating message ID and do not leak model file paths, secrets, or signing material.
- Unsigned candidates are labelled as such; no receipt/authorization claim is emitted.

## Merge and activation gates

Do not enable the dispatcher until all of the following are true:

1. The implementation is a separate reviewed follow-on stacked on the exact PR #164 head (or a deliberately updated base with a recorded comparison).
2. All focused dispatcher/challenge/approval tests pass.
3. Exact-head iOS LlamaEngine CI and companion workflows pass.
4. Static review confirms no page-controlled origin, session, approval, signer, or authorization bypass.
5. The bridge remains disabled by default if any prerequisite is unavailable.
6. Physical iPhone Air testing later verifies trusted workspace navigation, challenge replay rejection, cancellation, session replacement, and local generation.

Hosted simulator CI is not physical-device acceptance. A successful bridge test is not APEX authorization. A generated output is not signed evidence.
