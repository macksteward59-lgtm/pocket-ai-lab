# From a model checkpoint to an answer in Pocket AI Lab

The owner wants the current model to stay selectable while another model works, teaches, or becomes the base of a new version. The intended destination is one offline-first native iPhone workspace with a shared conversation, inspectable results and optional compute on a trusted host. This guide tracks the model workflow against that product vision.

## Follow one task

1. Open **Chat → Choose model** or **Model workshop** in the consumer web app.
2. Choose where to train. **This browser** imports v1 document-reader JSON or starts with either of the two published readers. **Local training host** uses compatible language-model snapshots installed on an explicitly configured loopback host.
3. Choose the **Base model**, **Teacher model** and candidate name. The candidate starts from the base. The teacher supplies training signals on reviewed examples. Training writes a separate artifact. Compare the base, teacher and candidate on the same held-out questions.
4. In the browser lane, choose **Save candidate to my readers**. On the host, **Train and save checkpoint** explicitly requests a new host checkpoint. Either saved candidate is eligible for another build. Saving a candidate does not assign it to agents or replace the configured chat provider.
5. Select the model under **Use a model** and choose **Use in Chat**. For a reader, the question and supplied passage travel with the selection. For a host language model, the submitted prompt goes to the selected local host. The reply identifies the model in the existing conversation. You can switch back to the configured chat model in the same transcript.
6. Choose **Review in Memory**, edit the proposed note and choose **Save memory**. Only this last action writes the note. The source field carries the model and passage or prompt digest. For a reader that selects a sentence, it also carries the sentence number. Candidate parent identities are included in the draft. Notes enter Memory as unverified.

### Running the host path

Start the consumer app with the training environment’s `python3` on its PATH and `POCKET_TRAINING_DIR` set to an absolute host-owned directory. The supported files are a local `config.json`, `tokenizer.json` and unsharded `model.safetensors` for a compatible dense Llama model up to 160 million parameters. The host uses a fixed synthetic document-verification recipe. The interface lets you select the models, run and compare them, and ask the candidate a question. Host imports are prepared on disk. Larger models, arbitrary training datasets and remote phone-to-host transport need separate support. [Host setup, format constraints and reproducible fixture](../../scripts/custom-gguf/workshop/README.md)

### What survives a restart

Saved reader weights, their local training record and both parent identities persist in the browser’s IndexedDB at the same origin. The browser can reopen the cached app and train another reader offline. Exported JSON includes portable weights and a declared training record. A fresh import validates the weights and treats its external history as unverified. Clearing site data removes the browser catalog. Host checkpoints live on the configured host. The web Memory store requires the local server and uses its existing storage and access controls. Chat turns and unsaved drafts are session state. Resuming general training with optimizer, scheduler and data position is a separate requirement from starting a new run at saved weights.
